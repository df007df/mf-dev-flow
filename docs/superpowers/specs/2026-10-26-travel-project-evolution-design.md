# 旅行清单项目连续演进示例设计

## 目标

将现有的旅行清单最小示例扩展为一个可重复演练的连续项目。读者从初版 PRD 和原型开始，依次完成原型分析、功能拆解、项目登记、单功能交付、需求变更、影响分析、重新规划与关联功能交付，最后在同一个本地看板中看到完整的功能演进结果。

示例必须解决三个问题：

1. 让第一次接触 `mf-dev-flow` 的读者知道每一步应该输入什么、执行什么、观察什么。
2. 用稳定的合成数据证明需求、原型、功能、验收 case、交付证据和变更影响可以串成一条链路。
3. 让最终看板同时呈现已完成功能、受变更影响的功能、重新规划后的关联功能及其依赖与历史。

## 范围

本次只维护一个“旅行清单”示例项目，不增加多个相互独立的示例项目。

包含：

- 初版和变更版 PRD。
- 初版和变更版可运行 HTML 原型。
- 五个连续 case 的稳定合成状态。
- 原型截图、应用效果截图和看板大截图。
- 每个 case 的场景、操作、预期效果、证据和下一步说明。
- 根 README 的演进索引。
- 最终状态下的完整功能演进看板。

不包含：

- 外部 API、登录、数据库或云服务。
- 将合成状态描述成真实生产交付。
- 为演示修改核心流程语义或降低现有门禁。
- 多个不同业务主题的 demo。

## 推荐实现方式

采用“版本化里程碑 + 可切换 fixture”的混合方式。

- 所有 case 共用一个应用和一个项目身份。
- 每个里程碑保存完整、可验证的 `.mf-dev-flow` 合成状态快照。
- 一个小型切换命令把指定里程碑投影为当前演示状态。
- 看板仍通过正式的只读读取路径加载当前状态，不为 demo 增加特殊展示逻辑。
- 最终里程碑保留完整历史，能够展示整个项目的演进，而不是只显示最终结果。

这种方式比只写静态文档更可操作，也比每次现场运行全部生成命令更稳定。快照是公开 fixture，必须在文档和数据中明确标注为合成演示状态。

## 真实生成原则

里程碑快照必须来自一次实际执行的 `mf-dev-flow` 工作流，不能通过直接拼装最终 `.mf-dev-flow` 真源文件来模拟结果。

- 项目登记、PRD 摄取与核验、原型分析、功能规划、交付、验收、变更影响和复评均使用本仓库公开的技能入口与 CLI 命令执行。
- PRD 原文、HTML 原型和产品代码属于项目输入或开发产物，不要求 CLI 自动生成；PRD `findings.json`、原型观察记录和功能 proposal 属于 Agent 按技能协议完成的分析产物，必须再经过对应的 `check`、`audit`、`accept`、`apply` 或交付门禁。
- `project.json`、功能地图、功能历史、运行状态和交付状态等规范真源不得绕过命令直接改成目标结论。
- 每个 Case 在真实流程达到对应状态后，才复制当时的 `.mf-dev-flow` 目录形成只读里程碑；快照脚本只负责复制和计算哈希，不参与生成业务结论。
- 每个里程碑保存无绝对本机路径的命令记录、输入记录、输出文件清单和 SHA-256 清单。公开复现指南必须说明哪些内容由用户提供、哪些内容由 Agent 分析、哪些内容由 CLI 生成或核验。
- Case 04 的 `review_required` 必须由实际 PRD/原型变化和旧规划基线之间的差异计算产生；Case 05 必须通过实际 `feature refine`、影响复评、`feature apply` 和交付命令收敛。
- 用户只安装 `mf-dev-flow` 技能，并使用正常的编辑、开发和浏览器取证能力，即可从公开输入重新产生同类状态；不得依赖私有脚本、隐藏服务或预制内部数据。

## 项目故事

### 初版需求

旅行者需要查看准备事项，并能切换“仅看已完成”。默认显示全部项目。

初版拆出：

- 功能组：旅行清单浏览。
- 功能点：仅看已完成项目。
- 验收 case：默认显示全部项目；筛选后只显示已完成项目；关闭筛选后恢复全部项目。

### 首次交付

“仅看已完成项目”完成开发和浏览器验证。看板记录原型对齐、技术方案、开发和端到端验收四个阶段，以及页面效果截图。

### 需求变更

PRD v2 和原型 v2 增加：

- 按出行阶段分组，例如“出发前”和“旅途中”。
- 当前筛选结果的进度摘要。

变更会影响已交付的筛选功能：筛选必须在分组结构下继续正确工作，进度摘要必须根据当前筛选结果计算，不能沿用旧的全量统计。

重新规划后形成：

- 调整后的产品功能：仅看已完成项目。
- 新产品功能：按出行阶段分组。
- 新产品功能：筛选结果进度摘要。
- 依赖关系：摘要依赖筛选结果；筛选与摘要都依赖新的分组数据结构。

## 五个连续 Case

### Case 01：冻结 PRD 与原型基线

场景：项目刚开始，先确认初版 PRD、原型入口、页面范围和公开数据边界。

操作：

1. 阅读 PRD v1。
2. 打开原型 v1。
3. 启动看板并检查项目、PRD 和原型来源。

效果：看板显示已经登记的项目、初版来源和等待分析的状态，不提前出现已完成开发结论。

截图：完整原型页面；看板中的项目与来源区块大图。

### Case 02：原型分析、功能拆解与项目登记

场景：从页面区域和交互中提取可观察事实，并拆出功能与验收边界。

操作：

1. 查看原型入口、列表区域和筛选控件。
2. 检查原型分析记录及来源截图。
3. 查看功能地图和验收 case。
4. 查看项目登记信息、原型入口、代码范围和验证命令。

效果：看板显示一个功能组、一个产品功能、来源证据、开发要求和三条验收 case；项目登记明确原型入口、代码根、允许写入范围和验证方式。

截图：原型分析区块大图；包含 case 卡片与所属功能卡片的功能分组大图。

### Case 03：交付第一个功能

场景：开发“仅看已完成项目”，并形成可核查的浏览器证据。

操作：

1. 切换到 Case 03 里程碑。
2. 打开应用，验证默认、筛选开启和筛选关闭三个状态。
3. 在看板查看四个交付阶段、写入边界和验收证据。

效果：筛选功能显示为已完成；每条验收 case 都有对应页面状态；范围外改动不被归入该功能。

截图：默认页面、筛选页面、恢复页面；完整功能卡和阶段证据区块大图。

### Case 04：PRD 与原型发生变化

场景：初版功能交付后，PRD v2 和原型 v2 增加分组与进度摘要。

操作：

1. 对比 PRD v1 与 v2。
2. 对比原型 v1 与 v2。
3. 运行或查看影响分析。
4. 在看板查看待复评提示与受影响功能。

效果：系统主动将已完成的筛选功能标记为需要复评，并列出变化来源、影响原因和关联范围；旧规划不能被静默继续使用。

截图：变更版完整原型；影响分析区块大图，必须包含变更提示、受影响功能卡和其所在分组。

### Case 05：重新规划并完成关联功能

场景：根据影响分析调整原功能，同时规划和交付分组、摘要两个相关功能。

操作：

1. 查看重新规划后的功能依赖、优先级和波次。
2. 打开最终应用，依次验证分组、筛选和进度摘要。
3. 在最终看板查看所有功能及历史。

效果：应用按阶段分组；筛选在分组内正确工作；摘要反映当前可见结果。最终看板同时展示原功能的历史、变更影响、复评结果、三个功能的依赖和交付状态。

截图：最终应用完整页面；最终功能演进看板大图；三个功能卡及 case 卡所在分组大图。

## 文档结构

示例目录更名为能表达长期演进含义的 `examples/travel-checklist-evolution/`，并保留根 README 对旧“五分钟示例”入口的迁移说明。

建议结构：

```text
examples/travel-checklist-evolution/
├── README.md
├── app/
│   ├── prototype-v1.html
│   └── index.html
├── prd/
│   ├── v1.md
│   └── v2.md
├── cases/
│   ├── 01-prd-and-prototype.md
│   ├── 02-analysis-and-planning.md
│   ├── 03-first-delivery.md
│   ├── 04-change-impact.md
│   └── 05-replanning-and-final-delivery.md
├── milestones/
│   ├── case-01/
│   ├── case-02/
│   ├── case-03/
│   ├── case-04/
│   └── case-05/
├── screenshots/
└── scripts/
    └── select-case.mjs
```

每个 case 文档使用相同模板：

1. 场景说明。
2. 当前输入和前置状态。
3. 操作步骤和可复制命令。
4. 应用效果。
5. 看板变化。
6. 大截图。
7. 生成的状态与证据。
8. 下一 case 为什么发生。

根 README 新增索引表，包含 case、难度、预计耗时、主要输入、最终输出和链接。示例 README 则承担完整演进导航。

## 截图规范

- 使用真实浏览器渲染，不使用手工拼图冒充运行结果。
- 看板截图至少覆盖区块标题、状态提示、case 卡、功能卡和所属分组。
- 应用截图至少覆盖页面标题、操作控件、相关内容区和结果摘要。
- 统一使用桌面宽视口，确保文字可读；必要时分为“应用结果图”和“看板上下文图”，不裁成孤立小卡片。
- 图片文件名包含 case 和内容，例如 `case-04-impact-overview.png`。
- 文档注明截图对应的里程碑和复现命令。

## 数据与状态约束

- 所有用户、项目、PRD、原型、运行与截图均为中性合成内容。
- 不包含本机路径、用户名、内部仓库名、客户名、令牌、Cookie 或私有 URL。
- 当前里程碑由切换脚本从只读快照复制生成；脚本不得访问示例目录之外的项目状态。
- 看板保持只读，并只监听 `127.0.0.1`。
- 里程碑保留真实执行时间；快照冻结后不再改写时间，保证后续截图和排序稳定。
- 合成的已完成状态必须拥有对应的可运行页面、验证步骤和截图证据。

## 验证

实现完成后至少执行：

1. 所有 JSON 文件可解析，里程碑可顺序切换且可重复。
2. 每个 case 的命令、链接和截图文件存在。
3. 应用浏览器验证覆盖初版筛选和最终分组、筛选、摘要组合。
4. 看板单测、类型检查和相关浏览器测试通过。
5. 核心 CLI 与项目/规划/交付相关回归通过。
6. README、case 文档和截图引用检查通过。
7. 当前树与 Git 历史执行项目名、固定路径和凭据扫描。
8. 最终看板截图人工核对，确认能看出功能提出、交付、受影响、复评和再次交付的演进。

## 完成标准

- 读者只通过根 README 即可选择并进入任一 case。
- 五个 case 使用同一个项目身份并组成因果连续的故事。
- 每个 case 都有场景、操作、大截图和效果说明。
- Case 04 能明确展示主动影响分析，而不是只在文字中声称发生了影响。
- Case 05 的最终看板能看到完整演进、三个关联功能和依赖关系。
- 示例可在无外部账号、无凭据、无网络服务的情况下本地复现。
- 五个里程碑均可追溯到真实的 `mf-dev-flow` 命令与通过的门禁；删除里程碑快照后，读者可按公开复现指南重新执行工作流，而不是手工重建最终 JSON。
