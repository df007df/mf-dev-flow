# 项目基线

目标是把一次口头确认变成可复用、可核对的 `.mf-dev-flow/project.json`，不依赖特定技术栈或产品名。

## 先确认，再保存

确认以下信息；用户已提供的内容直接复述为结论，缺失且会影响执行的内容才问用户。不要把猜测写成已确认。

| 信息                     | 必填 | 记录方式                                                           |
| ------------------------ | ---- | ------------------------------------------------------------------ |
| 项目名称、目标与当前背景 | 是   | `project.name`、`project.background`                               |
| 原型来源类型与位置       | 是   | `prototype.kind`、`prototype.location`                             |
| 原型访问方式             | 是   | 本地文件、URL、设计工具权限、导出包或录屏；写入 `prototype.access` |
| 代码根目录               | 是   | `codeRoots[]`，可多仓                                              |
| 原型版本基线             | 应有 | commit、文件 hash、设计文件版本、导出日期或“未提供”                |
| 测试入口                 | 应有 | 单测/e2e 命令；未知则明确待确认                                    |

原型类型至少区分：`html`、`figma`、`design-tool`、`app-build`、`video`、`image`、`other`。登记范围与分析能力分开：`prototype capabilities --json` 列出实际适配器，当前只有本地 HTML。真实可操作构建产物也需相应适配器与取证工具，不能仅凭登记承诺穷尽。其它类型先记录可观察范围及缺口。

使用脚本创建基线后，补全 `project.json` 中的 `access`、`version` 与 `testCommands`，然后把 `confirmedAt` 更新为当前时间。基线变更要在 `project.json.changeLog` 追加一条，说明谁确认了什么、为何变更。

## 项目卡片与检查门禁

项目卡片在 `.mf-dev-flow/projects/<project-id>.json` 与同名 Markdown 中保存一次可复核的本地开发项目检查结果。扫描只读登记项目文档的路径与指纹，绝不自动改写项目说明、开发约定、目录结构、测试说明或发布/线上环境说明。

- 项目卡片只适用于本地可开发项目：首次新增必须执行 `project add ... --check`；存量项目在开始开发或登记为目标项目之前执行 `project check`。检查必须真实验证本地启动、`test` 与 `test:e2e`；任一失败即卡片为 `failed`。仅参考的外部项目不得使用 `project add`，应走系统卡片运行。
- 文档：必须找到并保护项目说明、目录结构、测试、线上环境四类说明；开发约定可从 `AGENTS.md`、`CONTRIBUTING.md` 或项目说明登记。测试文档要能说明 test/e2e 如何执行；线上环境记录测试与生产地址、部署状态和 DB 变量或访问边界，不能记录连接串、账号、口令、Token 或 Key。
- 环境：记录当前 Node、项目声明的 Node 版本、包管理器和版本，以及实际执行的启动/test/e2e 命令。项目卡片还必须结构化记录 E2E 运行器、截图来源和 H5 是否可替代；任务登记与阶段确认按此字段执行，不能只依赖命令字符串。小程序卡片若声明微信开发者工具，则只接受 `simulator_screenshot` 的模拟器截图及对应自动化、console/network 证据。
- 只读参考：只有用户明确表示不修改、仅参考代码或数据时，建立 `system` 运行并更新系统卡片；它不运行启动/test/e2e，也不获得项目卡片资格。系统卡片必须保留只读边界。

## 多仓与来源冲突

代码可有多个根目录；每个根目录需要用途（例如 web、mobile、api）与只读/可写边界。只要一个功能跨多个可开发项目，还必须为每个代码根设置可机读的 `deliveryRoles`：`ui-client`（用户可见 UI 与交互交付）和/或 `api-provider`（业务接口、Mock、契约与服务）。项目卡片必须显示这项职责，任务计划则以 `--project <代码根>` 绑定实际交付目标，不能根据目录顺序猜测。

原型也可以有多个来源，但必须指定一个 `primary: true` 的产品基准。来源不可访问时，不启动穷尽式拆解；先记录为 `unavailable` 并请用户补齐访问方式。

登记路径不能证明当前工具已连接：启动取证前检查指定版本的访问方式、截图输出与追踪能力。项目检查卡片的历史通过只代表其记录的版本和环境；代码、依赖或环境变化后仍按现有 project check 门禁重新核验，不用旧通过替代本次测试。
